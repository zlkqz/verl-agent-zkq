## 执行与汇报规则

1. 大 TODO 严格串行。每项完成实现、测试和数据核验后，更新文档、在对话中汇报并暂停；得到用户继续指示后再开始下一项。遇到需要讨论的问题同样暂停依赖工作。
2. **每次停点必须同时有 Markdown 记录和可独立阅读的对话说明。**写清当前进度、实际实现内容/原因、核心代码路径与关键逻辑、测试结果与未验证范围、问题/待决事项和下一步。不能只报“完成”或只给文档链接。
3. 主入口只保留当前状态与导航；模块说明放 `docs/p2o/modules/<TODO编号>.md`，命令/证据放 `docs/p2o/test_records/<TODO编号>.md`，环境共性信息放环境文档，按次经过放实施日志。大 trace/token 输出单独保存 artifact，避免正文堆积。
4. 计划动态更新。发现算法/数据语义、源码/论文与计划不一致或未预期 diff，先记录事实、影响和选项，与用户讨论后更新相关设计和验收，再实施。已确认内容不反复询问。
5. 使用 Git 保存实现和文档。保留用户已有修改；正式长训练需另行安排。本机 8 张 A100 可用于有界功能调试。

详细停点模板与证据要求见[记录规范 §8.4](p2o/runtime_and_recovery.md#section-8-4)和[接手要求 §12](p2o/decisions.md#section-12)。

## 核心约束速览

原 GRPO 入口/trainer/脚本保持原行为；P2O 两消融分别建立入口与 trainer，共享通用组件。任务身份不含 seed；K=8 以显式 success 比例 ≤1/8 判难。本收集区间距 GEPA 完成至少 20 个原生 epoch 且独立难样本 ≥32 才触发；dev 下限 8、上限 50，比例 25% 仍是提案。

历史策略使用最终 selected 模板的实际成功证据并保留最近成功周期；失败救援策略只用重试 K 组更新。SimpleMemory 下每轮重新插模板；新入口 prompt 上限自动从 4096 加 2048 至 6144，恢复时幂等。CRM 采用 B：AUG 取自 rollout，BASE 一次评分复用。反思使用训练前固定模型，在 verl/Ray 独立 1 卡组运行，结束归还 GPU。

这些约束的详细定义及例外以主题文档为准；后续待做项不能视为当前功能。论文按 [arXiv v4](https://arxiv.org/pdf/2603.21877v4) 核对；最初源码阅读基准为目标仓库 `a4f930c` / 相邻只读 P2O 仓库 `92997e2`，当前实现版本以 Git 为准。
